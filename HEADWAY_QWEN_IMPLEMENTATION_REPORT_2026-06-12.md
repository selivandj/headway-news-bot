# Headway News Bot: отчет по внедрению улучшений и состоянию проекта

Дата: 2026-06-12  
Проект: Telegram-бот для канала `@headway74`  
VPS-путь: `/opt/headway-news-bot`  
GitHub-репозиторий: `selivandj/headway-news-bot`

## 1. Короткий итог

Бот не был полностью "мертвым": на VPS работали сервисы, а монитор создавал черновики. Основная проблема была в надежности и прозрачности: часть ошибок могла оставаться только в журнале VPS, а китайский дневной отчет читал старое состояние вместо свежего запуска парсеров.

Что сделано:

- исправлена ошибка в `monitor.py`, из-за которой обычный монитор мог падать после создания черновика;
- китайский дневной отчет теперь заново проверяет источники перед отправкой отчета;
- добавлены аварийные уведомления владельцу в Telegram при падении Telegram-бота;
- добавлены аварийные уведомления владельцу в Telegram при падении monitor-задачи;
- добавлен быстрый `smoke_check.py` для проверки проекта перед деплоем;
- добавлены первые статические тесты для будущего pytest/GitHub Actions;
- обновлен `.env.example`;
- изменения загружены на VPS и проверены там же.

Публикация по-прежнему остается ручной: бот присылает черновик, публикация только после ответа владельца `публикуй`.

## 3. Исправленная причина "бот вроде ничего не делает"

В `monitor.py` был риск падения при записи истории обычного черновика: использовалась переменная версии черновика, которая в обычном режиме не должна была использоваться. Из-за этого монитор мог дойти до создания файла, но дальше оборваться.

Исправлено:

- обычные черновики теперь записываются в историю по `aid`;
- версии после рерайта/медиа-исправления по-прежнему используют свой version id;
- добавлен тест, который следит, чтобы эта защита не пропала.

## 4. Китайские источники

Сейчас в проекте два уровня китайского поиска.

Первый уровень: стабильные RSS/новостные источники в общем потоке:

- `CnEVPost`;
- `CarNewsChina`;
- Google News RSS по EV/charging;
- международные EV-источники, где часто появляются китайские новости.

Второй уровень: прямой китайский сбор:

- `Sogou WeChat Search`;
- `D1EV`;
- `36Kr`;
- `Weibo` через поисковый fallback;
- дополнительный Baidu/SerpApi путь, если задан ключ.

Что исправлено:

- дневной китайский отчет больше не читает старый `test_state.json` как будто это свежий результат;
- перед отчетом он запускает `collect_china_candidates(24, force=True)`;
- затем обновляет `daily_stats.md`, `test_run.md`, `test_state.json`;
- после этого отправляет сводку владельцу.

Последняя свежая проверка китайских источников:

| Источник | Найдено | Медиа | Ошибки |
| --- | ---: | ---: | --- |
| D1EV | 6 | 3/4 | `502 x4` |
| 36Kr | 1 | 0/1 | нет |
| Sogou WeChat | 0 | 0/0 | `timeout x1` |

Вывод: китайский контур живой, но Sogou и часть D1EV нестабильны без хорошего китайского/азиатского прокси. Надежнее всего сейчас работают D1EV через листинги/Google fallback и 36Kr API/newsflash.

## 6. Что из Qwen не внедрялось сейчас

### Async SQLAlchemy / PostgreSQL

Отложено. Сейчас у проекта один владелец, один Telegram-бот, один monitor и SQLite достаточно. Переезд на async/PostgreSQL даст больше сложности, чем пользы, пока нет веб-админки, нескольких воркеров и высокой нагрузки.

### Redis

Отложено. Кэш сейчас можно держать файлово/SQLite. Redis нужен позже, если появятся:

- веб-админка;
- несколько процессов;
- много параллельных поисков изображений;
- очередь задач.

### APScheduler

Отложено. На VPS уже работает systemd timer, он проще и надежнее для текущего этапа. APScheduler имеет смысл, если вся логика расписаний переедет внутрь одного Python-приложения.

### Webhooks вместо polling

Отложено. Polling сейчас проще и устойчивее: не нужен домен, TLS, reverse proxy и открытый endpoint. Для текущего VPS polling достаточен.

### Docker / Docker Compose

Отложено до стабилизации кода и GitHub-репозитория. Сейчас важнее качество черновиков, медиа и обратной связи. Docker нужен позже для переносимости и CI/CD.

### Веб-админка

Отложено. Сейчас основной рабочий интерфейс владельца — Telegram, и это правильно для 14-дневной отстройки. Веб-админку лучше делать после накопления статистики и фиксации правил.

### Inline-кнопки

Полезно, но не внедрялось в этом шаге. Причина: кнопки требуют аккуратной привязки callback-data к конкретному черновику и защиты от случайной публикации не того поста. Это следующий хороший UX-шаг после стабилизации текущей логики.

## 7. Редакционные правила канала

Ключевой файл: `vps/channel_agent_rules.md`.

Главные правила:

- канал не для маркетологов;
- писать для людей, которые интересуются зарядками, EV, бизнесом на ЭЗС, покупкой и эксплуатацией станций;
- не использовать фразу "что можно забрать в работу";
- не писать "как пример для РФ";
- не называть новость российской, если она не про Россию;
- не публиковать шаблонные заготовки как готовые посты;
- не выдумывать факты;
- если оригинальная картинка есть — брать ее;
- если картинки нет — искать точную по сущности;
- генерация изображения только по явной команде владельца.

Эти правила должны оставаться выше конкретной модели: Gemini, Groq, OpenRouter, Kimi или OpenAI.

## 11. Текущий вывод

Проект стал устойчивее: теперь меньше шансов, что он молча сломается, а владелец ничего не узнает. Китайский отчет оживлен и снова делает свежий сбор. Редакционная память и правила канала остаются центральным механизмом, чтобы замена LLM-провайдера не превращала посты в шаблонный мусор.

Главный оставшийся риск — качество источников и медиа, особенно по китайскому контуру. Это не проблема модели как таковой, а проблема доступа к источникам, антибот-защит и точности поиска изображений.
