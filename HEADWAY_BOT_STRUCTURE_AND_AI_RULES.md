# Headway Telegram Bot: структура, оценка качества и правила для сторонних ИИ

Документ нужен как единая точка входа для любого разработчика или ИИ-агента, который будет дорабатывать бота. Цель: при замене модели, провайдера или промпта качество постов не должно резко меняться.

## 1. Главная логика проекта

Бот делает не автопостинг, а редакционный конвейер:

1. Ищет новости по теме EV, зарядных станций, электромобилей, инфраструктуры и смежных тем.
2. Оценивает, интересна ли новость русскоязычному читателю канала.
3. Достает факты из источника.
4. Генерирует черновик поста по правилам канала.
5. Ищет релевантные изображения.
6. Отправляет черновик владельцу в Telegram.
7. Публикует в канал только после явного ответа владельца: `публикуй`, `опубликуй`, `publish`.

Без подтверждения владельца публикации быть не должно.

## 2. Основная структура

### Корень проекта

`README-telegram-workflow.md`  
Краткое описание раннего Telegram-процесса.

`.env.example`  
Пример переменных окружения. В нем не должно быть реальных ключей.

`HEADWAY_BOT_STRUCTURE_AND_AI_RULES.md`  
Этот документ: архитектура, качество, правила для агентов и сторонних ИИ.

### Папка `vps/`

`vps/monitor.py`  
Главный монитор новостей. Он:
- собирает кандидатов;
- фильтрует нерелевантные материалы;
- выбирает LLM-провайдера;
- извлекает факты;
- применяет редакционные правила;
- валидирует качество текста;
- ищет и скачивает медиа;
- создает `.pending.json`;
- отправляет черновик на согласование.

`vps/bot.py`  
Telegram-бот согласования. Он:
- принимает ответы владельца;
- понимает, к какому черновику относится reply;
- публикует только выбранный черновик;
- умеет отменять черновики;
- принимает обратную связь;
- запускает поиск медиа или генерацию только по явной команде.

`vps/channel_agent_rules.md`  
Главный редакционный закон канала. Любая модель и любой внешний агент должны следовать этому файлу. Если есть конфликт между моделью и правилами, правила важнее.

`vps/editorial_memory.md`  
Накопленная память обратной связи владельца. Это дополнение к правилам, а не замена им.

`vps/draftctl.py`  
Вспомогательное управление черновиками.

`vps/parsers/`  
Парсеры и поисковые модули, включая китайское направление.

`vps/media/storage/images/`  
Скачанные изображения для черновиков.

`vps/drafts/`  
Черновики, ожидающие согласования. Формат: `*.pending.json`.

`vps/published/`  
Опубликованные посты. Формат: `*.published.json`.

`vps/cancelled/`  
Отклоненные или удаленные черновики.

`vps/feedback/`  
Логи обратной связи владельца.

`vps/database/history.db`  
SQLite-история статей и статусов, чтобы не гонять одни и те же материалы.

`vps/logs/llm_usage.md`  
Лог использования моделей. По нему проверяется, какая модель реально писала текст.

`vps/headway-news-bot.service`  
systemd-сервис Telegram-бота.

`vps/headway-news-monitor.service`  
systemd-сервис одного запуска монитора.

`vps/headway-news-monitor.timer`  
Обычное расписание монитора.

`vps/headway-news-monitor-hourly24.timer`  
Временный тестовый режим: запуск каждый час в течение 24 часов.

`vps/run_hourly_24h_monitor.sh`  
Скрипт суточного hourly-теста. Сам считает срок работы и отключает временный таймер.

## 3. Текущий принцип работы ИИ

Используется цепочка провайдеров:

1. `Gemini`
2. `Groq`
3. `OpenRouter`

OpenRouter сейчас полезен как резерв и доступ к free-моделям, но отдельные бесплатные модели могут ловить лимиты. Поэтому порядок можно менять по фактическому качеству и доступности.

Ключевые переменные:

```env
LLM_PROVIDER_CHAIN=gemini,groq,openrouter
TRANSLATION_QA_PROVIDER_CHAIN=gemini,groq,openrouter
LLM_TEMPLATE_FALLBACK=1
ALLOW_RULE_BASED_DRAFTS=0
```

Важно: `ALLOW_RULE_BASED_DRAFTS=0` означает, что rule-based шаблон не имеет права создавать готовый пост для канала. Если все ИИ недоступны, лучше не прислать пост, чем прислать техническую чушь.

## 4. Роли ИИ в системе

ИИ не является владельцем канала и не принимает решение о публикации.

Допустимые роли ИИ:
- извлечь факты из статьи;
- перевести и нормализовать смысл;
- собрать краткий черновик;
- проверить семантику перевода;
- предложить улучшение формулировки;
- классифицировать релевантность новости.

Запрещенные роли ИИ:
- публиковать без владельца;
- добавлять непроверенные факты;
- придумывать изображение как будто оно из новости;
- менять аудиторию канала;
- писать служебный шаблон как будто это пост;
- игнорировать `channel_agent_rules.md`.

## 5. Контракт для любой модели

Модель на этапе извлечения должна возвращать только JSON:

```json
{
  "headline": "русский заголовок с конкретным смыслом или цифрой",
  "lead": "1-2 коротких предложения по сути новости",
  "details": [
    "короткий факт 1",
    "короткий факт 2",
    "короткий факт 3",
    "короткий факт 4"
  ],
  "takeaway": ""
}
```

В JSON запрещены:
- emoji;
- ссылки;
- markdown;
- китайские символы;
- рекламный тон;
- фразы "для маркетологов", "главное коротко", "что можно забрать в работу", "как пример для РФ";
- служебные фразы "тема материала", "источник и регион", "ключевые цифры в тексте".

Финальный Telegram HTML собирает код, а не модель.

## 6. Правила хорошего поста

Хороший пост:
- понятен без открытия источника;
- содержит конкретную новость;
- дает практический смысл для владельца ЭЗС, водителя, бизнеса, ЖК, парковки, флота или оператора;
- имеет цифры, если они есть в источнике;
- не превращается в лекцию;
- не делает искусственный вывод про РФ;
- не выглядит как пресс-релиз;
- заканчивается ссылкой на источник.

Плохой пост:
- начинается с "Новость по зарядной инфраструктуре";
- пишет "Источник сообщает о событии";
- просит "сверить детали по оригиналу";
- содержит "Тема материала", "Источник и регион", "Ключевые цифры в тексте";
- пересказывает заголовок и ничего не добавляет;
- берет слабую новость без зарядного смысла;
- использует случайные картинки;
- называет иностранную новость российской только из-за русского языка источника.

## 7. Медиа

Приоритет:

1. Оригинальные изображения из статьи.
2. Изображения с других страниц по точному названию станции, модели, компании или события.
3. Черновик без медиа с пометкой, что медиа не найдено.
4. Генерация только после явной команды владельца.

Нельзя использовать:
- дубли и почти одинаковые фото;
- QR-коды;
- логотипы вместо события;
- скриншоты соцсетей без смысла;
- случайные стоковые картинки;
- нерелевантные авто, людей, сцены, баннеры;
- небезопасный широкий поиск по интернету.

Если в статье 5 картинок, но только 1 относится к зарядке, брать только 1.

## 8. Оценка эффективности

Оценивать нужно не только "бот прислал пост", а качество редакционного результата.

### Основные метрики

`drafts_created`  
Сколько черновиков создано за день.

`approved_count`  
Сколько черновиков владелец опубликовал.

`rejected_count`  
Сколько черновиков отклонено.

`approval_rate`  
`approved_count / drafts_created`. Главная метрика качества подбора и текста.

`media_success_rate`  
Доля черновиков с релевантными изображениями.

`bad_media_count`  
Сколько раз владелец указал, что картинки плохие.

`provider_success_rate`  
Сколько раз каждый провайдер успешно дал валидный JSON и прошел проверку.

`provider_reject_rate`  
Сколько раз провайдер дал мусор, ошибку, невалидный JSON или пост с запрещенными фразами.

`freshness_hours`  
Возраст новости на момент черновика.

`source_quality`  
Какие источники чаще дают хорошие посты.

`owner_feedback_reuse`  
Учитывается ли обратная связь владельца в следующих постах, а не только в одном черновике.

### Минимальные целевые ориентиры

На этапе отстройки:
- 1-3 черновика в день;
- ручное согласование всегда включено;
- approval rate стремится к 50%+;
- template/rule-based постов в Telegram: 0;
- плохих случайных картинок: 0;
- каждая ошибка владельца превращается в новое правило или валидатор.

После отстройки:
- можно думать о частичной автоматизации только для источников и тем, где approval rate стабильно высокий;
- полная автопубликация без владельца не включается, пока нет устойчивого качества текста и медиа.

## 9. Улучшение кода

Любое изменение должно отвечать на вопрос: оно повышает качество поста, надежность, безопасность или управляемость?

Приоритеты улучшений:

1. Жесткие валидаторы качества текста.
2. Логирование причины отказа по каждому кандидату.
3. Раздельная статистика по провайдерам.
4. Учет обратной связи владельца как глобальных правил.
5. Улучшение поиска реальных изображений по точным сущностям.
6. Защита от дублей статей и дублей картинок.
7. Тестовые прогоны без публикации.
8. Простые отчеты: что найдено, что отклонено, почему.

Не улучшать код так:
- не добавлять новый дизайн процесса вместо точечной правки;
- не включать автопубликацию ради удобства;
- не ослаблять фильтры ради количества;
- не добавлять "универсальный шаблон поста", который маскирует отсутствие ИИ;
- не хранить реальные API-ключи в markdown, git или публичных файлах.

## 10. Проверка перед запуском

Перед включением расписания:

1. Проверить синтаксис:

```bash
python -m py_compile /opt/headway-news-bot/monitor.py /opt/headway-news-bot/bot.py
```

2. Проверить, что бот активен:

```bash
systemctl is-active headway-news-bot.service
```

3. Проверить таймер:

```bash
systemctl list-timers --all headway-news-monitor.timer --no-pager
```

4. Проверить провайдеров коротким запросом.

5. Сделать один контрольный запуск:

```bash
cd /opt/headway-news-bot
.venv/bin/python monitor.py --hours 24 --send-review
```

6. Убедиться, что новый черновик не `template rule-based`.

## 11. Как стороннему ИИ дорабатывать проект

Перед изменениями агент обязан прочитать:

1. `HEADWAY_BOT_STRUCTURE_AND_AI_RULES.md`
2. `vps/channel_agent_rules.md`
3. `vps/monitor.py`
4. `vps/bot.py`
5. последние 5-10 файлов из `vps/drafts`, `vps/published`, `vps/cancelled`
6. `vps/logs/llm_usage.md`, если есть вопрос к модели

Агент должен:
- сохранять ручное согласование;
- не публиковать без владельца;
- не раскрывать ключи;
- не делать массовые переписывания без причины;
- после изменения проверять синтаксис;
- объяснять, какая проблема исправлена;
- фиксировать новую обратную связь как правило или валидатор.

## 12. Красные линии

Нельзя:
- выпускать посты без согласования владельца;
- использовать rule-based шаблон как готовый пост;
- писать политический контекст там, где его нет в новости;
- называть зарубежную новость российской;
- генерировать "фото события";
- брать случайные картинки из интернета;
- публиковать пост, если источник невалидный;
- скрывать, какая модель написала черновик;
- игнорировать плохие отзывы владельца как "одноразовую правку".

Если есть сомнение, лучше отправить владельцу честное сообщение: "новость есть, но качество черновика/медиа не проходит правила".
